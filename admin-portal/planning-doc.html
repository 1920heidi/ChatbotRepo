01

Context

The admin portal currently has one flat tier: any logged-in admin can do everything, and every document is visible to everyone with no ownership or department attached to it.

This plan adds three role tiers — Super Admin grants access and oversees everything; Reviewer uploads and approves or manages documents; Uploader submits documents only — plus department-scoped visibility, so an admin only sees their own department's documents unless they're a Super Admin, who sees across all departments. It also extends what can be done to a document once it's in: replace it with full version history, or archive it as a recoverable soft-removal distinct from permanent delete.

Exploration of the existing code found: admin_users has no role column, documents has no uploaded_by, createAdmin is reachable by any admin today, and the existing approved column — added earlier, never enforced — is the natural fit for a real review gate.

Confirmed with the user

  • One department per admin, assigned by the Super Admin — not a login-time picker. Login stays plain email and password; the account's fixed department drives visibility automatically.
  • Super Admin sees documents across all departments.
  • Replacing a document keeps full version history — old files stay retained and downloadable.
  • Archiving removes a document from chatbot answers and the main list, but keeps it recoverable in a separate Archived view.
  • Uploader-submitted documents require Reviewer or Super Admin approval before the chatbot can use them.
  • The Conversations page (chat transcripts) is Reviewer and Super Admin only.
02

Role & department model

Three fixed roles, stored on admin_users.role. Visibility and write access both key off role; document visibility additionally keys off department.

Action Uploader Reviewer Super Admin
Upload a document ✓own dept ✓own dept ✓any dept
View documents own uploads only own department, all uploaders all departments
Approve / revoke approval ✕ ✓ ✓
Replace (new version) ✕ ✓ ✓
Archive / restore ✕ ✓ ✓
Permanently delete ✕ ✓ ✓
Confidential toggle (doc / section) ✕ ✓ ✓
View conversations ✕ ✓ ✓
Create admins / roles / departments ✕ ✕ ✓

documents.approved now defaults from the uploader's role at upload or replace time — computed server-side from the verified session token, never from client input: false (pending) for an Uploader, true (auto-cleared) for a Reviewer or Super Admin. This also closes a latent gap: approved is technically client-suppliable in the request body today, even though the current upload form never sends it.

03

Database

db/init/003_add_roles_departments_versions.sql — applied to a fresh install automatically, and run directly against the live database too, since init scripts only execute once, on an empty volume.

003_add_roles_departments_versions.sql
CREATE TABLE departments (
  id         UUID PRIMARY KEY,
  name       TEXT NOT NULL UNIQUE,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

ALTER TABLE admin_users ADD COLUMN role TEXT NOT NULL DEFAULT 'reviewer'
  CHECK (role IN ('super_admin', 'reviewer', 'uploader'));
ALTER TABLE admin_users ADD COLUMN department_id UUID REFERENCES departments(id);

ALTER TABLE documents ADD COLUMN uploaded_by UUID REFERENCES admin_users(id);
ALTER TABLE documents ADD COLUMN department_id UUID REFERENCES departments(id);
ALTER TABLE documents ADD COLUMN archived BOOLEAN NOT NULL DEFAULT FALSE;
ALTER TABLE documents ADD COLUMN archived_at TIMESTAMPTZ;
ALTER TABLE documents ADD COLUMN current_version INTEGER NOT NULL DEFAULT 1;

CREATE TABLE document_versions (
  id              UUID PRIMARY KEY,
  document_id     UUID NOT NULL REFERENCES documents(id) ON DELETE CASCADE,
  version_number  INTEGER NOT NULL,
  filename        TEXT NOT NULL, -- original filename, for display / download
  stored_filename TEXT NOT NULL, -- multer-generated name; each container
                                -- builds its own path from its own uploads dir
  source          TEXT NOT NULL,
  chunks_indexed  INTEGER,
  uploaded_by     UUID REFERENCES admin_users(id),
  uploaded_at     TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE (document_id, version_number)
);

-- The already-seeded admin becomes the first super admin
-- (no-op on a fresh install, where admin_users is still empty here).
UPDATE admin_users SET role = 'super_admin' WHERE email = 'admin@psc.go.ke';

documents keeps mirroring the current version's filename, file_path, source, and chunks_indexed — as it already does — so every existing query that reads from documents keeps working unchanged. document_versions is the append-only history sitting alongside it. department_id stays nullable on admin_users: required in the application layer for Reviewer and Uploader accounts, not required for Super Admin, whose access isn't department-scoped.

Migration consequence

The two documents already in the live database — uploaded before this feature existed — will have uploaded_by = NULL and department_id = NULL after migration. Since Reviewer visibility filters by department, they'll become invisible to every Reviewer (only Super Admin, who sees everything, still will) until a Super Admin manually assigns them to a department. Worth doing right after migrating.

04

Archive & restore reuse existing machinery

No Python changes needed

Archiving a document deletes its Qdrant vectors — reusing the existing delete_by_document_id / deleteDocumentVectors, unchanged — and sets documents.archived = true. Restoring clears the flag and re-enqueues ingestion via the existing enqueueIngestion, rebuilding vectors from the current version's file — the same path Reindex already takes.

No new Qdrant payload field or rag-service filter is required for archiving: it's pure Node orchestration of endpoints that already exist. rag-service and ingestion-worker are untouched by this part of the plan.

05

Retrieval enforcement — the one new piece in rag-service

app/retrieval/search.py gains must: approved == True alongside the existing must_not: confidential == True. Safe as a hard must — unlike confidential — because every point ever written already has approved set, defaulting True historically, so there's no legacy-gap risk of hiding old content by accident.

Mirrors the confidential-toggle plumbing already proven in the codebase:

app/vector_store/qdrant_client.py
add set_approved(document_id, approved)
app/api/documents.py
add PATCH /documents/{document_id}/approved

08

Verification

End-to-end, run in order against the live stack:

  1. Apply 003_...sql to the live database; confirm admin@psc.go.ke is now role = 'super_admin'.
  2. Rebuild and restart rag-service and chatbot-backend; confirm both come up clean.
  3. As Super Admin: create a department, a Reviewer and an Uploader in it, then a second department with its own Reviewer, to prove isolation.
  4. Log in as the first Uploader, upload a document, confirm it shows Pending review with only Sections visible — and that the second department's Reviewer cannot see it.
  5. Query rag-service directly; confirm the bot does not yet use the pending document's content.
  6. Log in as the first department's Reviewer — the document is visible, the Uploader isn't — and approve it.
  7. Re-query the bot; confirm it now uses the content and cites the document.
  8. As that Reviewer, replace the document with a new file. Confirm a new version row exists, the old file is still downloadable from the version list, and the bot's answers reflect the new content.
  9. Archive the document; confirm it disappears from the main list and from bot answers, but appears in the Archived view. Restore it; confirm it's searchable again.
  10. Confirm the Uploader account is redirected away from Users, Conversations, and Archived Documents.
  11. Attempt to demote the only Super Admin; confirm it's rejected with a clear error.
  12. Call the new user, department, version, and archive endpoints with an Uploader's token; confirm 403 across the board.
